# 手动构建与切换 sing-box 内核

默认不自动查新、不自动升级。工作流只有 `workflow_dispatch`，没有定时或 push 触发。

## 在 GitHub 构建

将工作流提交到默认分支后，进入 Actions → **Build agent with selected sing-box** → Run workflow。

| 输入 | 含义 |
|---|---|
| channel | `stable` 稳定版 / `prerelease` 预发布版，默认 stable |
| sing_box_version | 指定 sing-box 版本，可带 v；留空取所选通道的官方最新版本 |
| sbx_version | agent 的基线 sbx 正式版本；留空取本项目最新正式版 |

指定版本必须属于所选通道。例如 `1.15.0-alpha.13` 应选择 prerelease。

构建固定使用已发布 sbx 标签的源码提交，不跟随主分支。只在 Runner 临时目录修改
`agent`、`e2e`、`spike` 的 go.mod/go.sum，不提交、不推送依赖更新，不自动修改业务源码。
准备完成后，测试和产物构建使用同一份依赖文件。

现有 ci.yml 保留 push、pull_request 和手动入口，增加可复用入口。普通推送仍测试该次提交和
仓库锁定的依赖；内核工作流调用可复用入口，传入固定源码提交及临时依赖文件。
不是依赖机器人 push 再触发 CI，因此不受 GITHUB_TOKEN 阻止递归触发的影响。

全部 CI 通过后才构建、发布两个 Linux 架构的 agent。编译/测试失败就停止，正式版本保持不变。

## 命名与重复构建

版本号不是固定的。每次运行默认读取当时最新的 sbx 正式版，并使用该标签对应的源码。
通用命名规则为 `sbx-agent-v{正式版版本}-singbox-v{内核版本}-linux-{架构}`。

以下以正式版 v0.4.38 为例，正式包的命名保持不变：

```
sbx-agent-v0.4.38-linux-amd64
sbx-agent-v0.4.38-linux-arm64
```

内核变体：

```
sbx-agent-v0.4.38-singbox-v1.14.4-linux-amd64
sbx-agent-v0.4.38-singbox-v1.14.4-linux-arm64
```

发布 v0.4.39 后，再运行同一个工作流会自动基于 v0.4.39 构建，例如
`sbx-agent-v0.4.39-singbox-v1.14.4-linux-amd64`。已有 v0.4.38 变体保留原名，不改名、不覆盖。
只有显式填写 `sbx_version` 时，才会选择指定的历史正式版。

两者均带架构后缀，不能省略。内核变体发布到独立标签
`agent-v0.4.38-singbox-v1.14.4`，包含两份二进制、两份 `.sha256` 和 `kernel-manifest.json`。
不会设为项目的 Latest，也不会改变原安装脚本选择的正式版本。

清单记录 agent 版本、内核版本、稳定/预发布通道、源码提交、协议版本、CI 地址、依赖摘要及产物 SHA-256。
同一版本组合已经完整发布时直接复用，不覆盖产物。已有清单与源码提交不符时拒绝复用。
上传中断会留下草稿；检查并删除失败草稿后可重试，不自动覆盖已发布版本。

## 在主控切换

服务管理页选中被控 → `u` 升级菜单 → `k` 选择内核版本。

- 默认只更新选中机器，也可选择全部在线被控。
- 稳定版和预发布版分开选择。
- 版本留空表示该通道**最新已成功构建**的版本，不是尚未构建的官方版本。
- 指定已构建的旧版本可回退；返回原升级菜单按 `u` 可恢复当前 sbx 正式版自带的内核。
- 只接受与主控 sbx 版本、通信协议匹配的清单，校验下载地址和 SHA-256 后才下发。
- 被控重启后通过已有握手上报实际内核版本。切换会短暂中断代理连接。

主控不会代替用户触发 GitHub 构建，也没有新增常驻查新任务。
这里的 CI 证明预设配置通过回归，并不等于任意自定义配置都兼容任意内核版本。
